# BaiSapar — конкурентная очередь и закрытие стоянки

## Что воспроизведено до исправления

Локальный PostgreSQL/Docker, отдельная стоянка и шесть сервисных фикстур водителей; владелец входил обычным локальным password flow.

- Пять серий из шести одновременных `joinQueue`: в каждой серии пять запросов падали с `23505`, принимался только один водитель. Причина: конкурентный `MAX(queue_seq)+1` без блокировки стоянки.
- Одновременный отъезд первой машины, выход второй и вступление четвёртой возвращали три успешных ответа, но оставляли три live-записи вместо двух. `refreshBoardingSlots` записывал WAITING/BOARDING по старому снимку даже поверх LEFT/DEPARTED.
- Пять гонок «закрыть стоянку / добавить водителей» оставляли 1–2 live-машины на уже закрытой стоянке.
- Изменение владельцем `boardingSlots` с 1 на 2 не переводило вторую машину в BOARDING до следующего события очереди.
- Реальный браузер: закрытие последней стоянки вызывало `TypeError: …remove is not a function` при размонтировании карты. Реестр хранит `{ marker }`, а cleanup обращался к самому объекту записи как к Marker. React boundary скрывал ошибку от `pageerror`.

Первый E2E-проход ошибочно считал исчезновение брони успехом, хотя исчезал весь экран. Ошибку обнаружил просмотр скриншота, затем усиленный тест воспроизвёл её как FAIL. Старый unit-тест cleanup тоже проверял строку ошибочного кода, а не выполнение; заменён исполняемой проверкой реестра.

## Исправления

- Структурные изменения сериализуются блокировкой строки **конкретной стоянки** до блокировки очереди: вступление, отъезд, выход, передача и автоматическое освобождение. В dispatch/передаче строки водителей блокируются раньше стоянки; после стоянки новые driver-lock не берутся.
- Пересчёт посадки дополнительно ограничен live-статусами: закрытая запись не может «воскреснуть».
- Owner PATCH/DELETE: проверка, изменение, очистка очереди/броней и аудит в одной транзакции под тем же stand-lock. Уведомления отправляются после commit. Изменение boardingSlots сразу пересчитывает очередь и рассылает её обеим ролям.
- Sweeper обрабатывает стоянки по одной, транзакционно; порядок блокировок stand → entries → reservations соответствует подтверждению/отмене брони. После ожидания блокировки свежесть проверяется снова. Добавлен необязательный `standId` для изолированных интеграционных проверок.
- Вызов автоматического освобождения через обычный pool.query теперь сам открывает транзакцию; вызов с transaction client сохраняет транзакцию dispatch.
- Старый `stands-queue-db-check.js` требует явно заданную локальную БД и запускает sweeper только на собственной стоянке.
- Web cleanup карты удаляет реальные объекты Marker из обёрток, затем очищает реестр; повторный cleanup безопасен.

## Что не доказано этим этапом

Это проверки конкретных конкурентных сценариев, не нагрузочная аттестация на тысячи пользователей. Нет проверки на физическом телефоне и полевого QA навигатора. Внешние блокеры SMS/платежей/реестров сохраняются. Следующий UX-шаг — явное объяснение причины потери стоянки/брони на экране web и Flutter, а не только обновление списка и отдельное уведомление.
